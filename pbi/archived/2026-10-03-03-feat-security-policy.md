# PBI: SECURITY.md（脆弱性の報告窓口）を整備する

provsync の利用者として、秘密の漏えい経路などの脆弱性を非公開で報告する方法を知りたい、なぜなら API キーを含みうる設定を扱うツールで、公開 Issue に詳細を書くと被害が広がるから

## 実装ガイド（この順に実施。先に [00-implementation-guide.md](00-implementation-guide.md) を読む）

### 先に読むファイル
`README.md` の「秘密情報の扱い」節と「安全設計」節、`AGENTS.md` の Gotchas の秘密に関する項。`go.mod` の module 名（リポジトリは `github.com/armaniacs/provsync`）。

### 手順
1. リポジトリ直下に `SECURITY.md` を作る。内容は次のひな形を基にする（日本語。経緯や履歴は書かない）。

```markdown
# セキュリティポリシー

## 報告方法

脆弱性を見つけた場合は、公開の Issue に書かず、GitHub の「Report a vulnerability」（Security タブ > Advisories）から非公開で報告してください。

報告には、再現手順、影響を受けるバージョン、想定される影響を含めてください。実際の API キーなどの秘密は含めないでください。

## 対応方針

- 受領の確認は 7 日以内を目安とします。
- 修正は最新のマイナーバージョン系列のみを対象とします。
- 修正版のリリース後に、報告者の同意を得て内容を公開します。

## 対象範囲

provsync は設定ファイルの provider エントリを同期します。次のものは報告の対象です。

- 秘密（`apiKey`、`token` など）が、出力・ログ・中央設定・バックアップ以外の場所へ書かれる、または意図せず表示される問題
- バックアップや状態ディレクトリの権限に起因する情報漏えい
- 設定ファイルの破損や、意図しないファイルの上書きにつながる問題

## 秘密の取り扱い（設計）

- 中央設定には環境変数名（`apiKeyEnv`）のみを保持し、秘密の値は保持しません。
- push は対象ツールのファイルにある既存の秘密を削除せず保持します。
- バックアップには、書き込み前のファイルの内容（ファイル内の秘密を含みうる）が保存されます。
```

2. `README.md` の「秘密情報の扱い」節の末尾に `脆弱性の報告方法は [SECURITY.md](SECURITY.md) を参照。` を足す（日本語節と English 節の両方）。
3. CHANGELOG `[Unreleased]` の `Docs` に `SECURITY.md を追加` と書く。

### ユーザーへ確認が要る作業（勝手に実行しない）
GitHub の非公開の脆弱性報告を有効化する操作（リポジトリ設定 > Code security > Private vulnerability reporting）は外部へ影響する設定変更。実行前に必ずユーザーへ確認する。手元では `SECURITY.md` の追加までを完了とし、有効化は報告して依頼する。

### 注意
- 上記の「7 日以内」などの数値は目安であり、変えるならユーザーに確認する。
- 「安全が保証される」などの断定表現を書かない。
